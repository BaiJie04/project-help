# 跨平台使用协议

## 目标

同一套方法、状态格式和核心提示词应能用于不同模型与 AI 软件。平台专属能力只能作为增强，不能成为核心工作流的硬依赖。

## 能力检测

开始操作前确认：

- 是否能读取仓库和 `.project/project.json`。
- 是否能写入文件。
- 是否能执行 Python。
- 是否能读取 Git 状态并执行 Git 命令。
- 是否能发现 `SKILL.md` 并读取 references。

无法确认的能力按不可用处理。不得根据产品名称猜测能力。

## 三种模式

### Skill Mode

平台可发现 `SKILL.md`。只读取当前操作需要的 workflow reference，然后按契约执行。

### File Mode

平台不能发现 Skill，但能读取文件。将 `SKILL.md` 作为系统提示词或自定义指令，允许模型读取 `references/` 和 `.project/`。

### Chat Mode

平台不能访问文件。用户提供完整的当前 `project.json`，模型返回：

1. 操作结果。
2. 状态变更摘要。
3. 完整的候选 `project.json`。
4. Git 建议命令或 Git 不可用说明。
5. 下一步行动。

Chat Mode 不得声称已经写入文件或提交 Git。

## 统一响应契约

每次工作流响应都必须包含：

1. **操作结果**：完成了什么分析或变更。
2. **状态变更摘要**：新增、修改、完成的实体，以及 revision 变化。
3. **完整候选状态**：发生变更时提供完整 JSON，不提供省略关键上下文的片段。
4. **Git 建议**：给出 scoped commit message；如果 Git 不可用，明确说明没有版本记录。
5. **下一步行动**：一个可立即执行的下一步。

没有接受状态变更时，明确说明未修改文件。

## 降级规则

- 有文件读取但没有写入：只生成候选 JSON，不声称已保存。
- 有写入但没有脚本：手工执行全部校验规则，再原子写入。
- 有脚本但没有 Git：正常更新文件，只输出提交建议。
- 有 Git 但没有用户确认：不得提交。
- 不能读取 references：要求用户提供 `SKILL.md`、当前工作流说明和完整状态。

## Git 协议

- 提交前展示将包含的文件和提交消息。
- 默认只提交 `.project/project.json` 与 `.project/PROJECT.md`。
- 不修改工作区中的无关文件。
- 提交类型使用 `project(init|plan|update|review|close): <summary>`。
- 永不自动 push。

## 平台适配边界

核心文档不写死工具名称、绝对路径或平台专属调用。平台适配层可以映射“读取状态”“执行校验”“生成视图”“提交 Git”这些抽象操作，但不得改变状态 schema 或完成规则。
