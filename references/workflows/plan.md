# Plan 工作流

## 目标

把项目目标拆分为里程碑、迭代、工作项、依赖和可验收结果。

## 前置条件

- 读取并校验当前 `project.json`。
- 项目状态不应为 `completed` 或 `archived`。

## 执行步骤

1. 从项目目标和成功标准推导里程碑，不把普通任务直接当作里程碑。
2. 为当前执行窗口创建或更新迭代，明确迭代目标。
3. 创建工作项，选择正确的 `type`、`priority` 和验收标准。
4. 使用现有 ID 建立 `milestone_id`、`iteration_id` 和 `parent_id`。
5. 建立 `depends_on`，检查悬空引用、自依赖和依赖环。
6. 保持 backlog 顺序能够表达规划优先级。
7. 展示新增和修改内容、revision 变化和下一步行动。
8. 获得确认后写入完整候选状态并重新生成 `PROJECT.md`。
9. 建议提交：`project(plan): add <summary>`。

## 质量规则

- 每个工作项至少有一个可观察验收标准。
- 不为了填满计划而创建低价值任务。
- 当前迭代只保留可完成的重点，其余工作保持 `backlog` 或 `ready`。
- 依赖未满足时不要假装工作项可立即开始。

## Chat Mode

返回完整候选 JSON。不得省略未修改实体，否则用户无法安全替换当前状态。

## 示例

用户请求：“把文档站拆成第一个里程碑和一周迭代。”

预期效果：新增里程碑、迭代、epic/story/task 工作项，并建立依赖和验收标准；所有 ID 唯一，revision 增加 `1`。
